# C3 Pass 1 — Reconstruction Mechanics Boundary

Date: 28 September 2026. Scope: characterization and architectural validation only. No production code was changed.

## Phase and failure map

| Phase | Transaction owner and effects | Authority read/write | Failure residue and retry | Boundary |
| --- | --- | --- | --- | --- |
| 1. Backup and manifest validation | `RestorePreflightService.validate()` parses `manifest.json`, checks the dump exists and SHA-256 matches. Filesystem reads only; no shared transaction with later phases. The digest ties two local files together, not to an authenticated publisher. | Parses bounded authority metadata from the manifest. | Target untouched; retry after correcting input is safe. | Mechanics input validation. |
| 2. Pristine-target preflight | Read-only `BackupStateInspectionService.inspect()` uses its own repeatable-read transaction; `_check_target_is_pristine()` uses another repeatable-read transaction and counts non-allowlisted tables. Version, migration checksum and schema compatibility checks follow. | Reads canonical `security_state`; no writes. | Target untouched; retry safe. There is no lock spanning preflight and restore, so concurrent target changes are outside this guarantee. | Mechanics guard. |
| 3. Restore-list planning | `pg_restore --list` child process, target FK query through a read connection, temporary list-file write. Rejects duplicate included table-data entries and cycles; comments out `security_state` and migration-ledger table-data entries. | Reads archive TOC, but excludes protected table data from import. | Temporary directory cleans up; target untouched; retry safe. | Mechanics. |
| 4. `pg_restore` | External `pg_restore --data-only --single-transaction --exit-on-error --no-owner --no-privileges --use-list`. PostgreSQL transaction is owned by the child process, separate from application transactions. | Imports historical unprotected rows, including recovery and authorization history; cannot import canonical `security_state` table data through the selected list. | Failed child transaction rolls back its import. Successful import is durable even if a later phase fails. A successful import makes the target non-pristine, so the whole workflow cannot simply be rerun. | Mechanics. |
| 5. Historical authority reconstruction | `_apply_restored_authority()` uses `target_engine.begin()` and updates the singleton row from the validated manifest. Sets stored state, version and epoch; clears all bootstrap fields. | Writes canonical authority metadata, including a possible `NORMAL` state, with no fence. No new context or authorization is issued. | Update rollback on its own failure; prior import remains. If committed, authority remains unfenced on later failure. Full retry fails preflight when imported rows exist. | Currently mechanics, but it creates the unsafe interphase state described below. |
| 6. Migration | `run_migrations()` uses one initial transaction and separate transactions per migration, each with a transaction-scoped advisory lock. It may alter schema and migration ledger. | Does not intentionally issue recovery authority; migrations can affect schema used by authority records. | Earlier migrations may commit before a later failure; import and authority update remain. Full retry denied by non-pristine target. A migration `RuntimeError` is not normalized by `_restore_verified_data()`. | Mechanics. |
| 7. Post-restore inspection and validation | Read-only repeatable-read inspection compares state/version/epoch and requires no pending fence; `_verify_critical_tables()` independently runs `SELECT 1 ... LIMIT 1` against three critical tables. | Reads canonical authority. | No new writes; prior commits remain. Critical-table checks establish accessibility, not populatedness or source equivalence. Full retry denied when data was imported. | Mechanics checks. |
| 8. Recovery bootstrap | `_enter_recovery()` opens a Session; `AuthorityBootstrapService.initialize(RECOVERY)` locks singleton row and commits pending fence, origin fields and version +1, or rolls back an already-pending invocation. | Effective state becomes `RECOVERY_REQUIRED`; stored historical state and epoch remain. | Failed transaction rolls back its own change. If committed, later failure leaves the fence. Reinvoking bootstrap itself is idempotent while pending, but `reconstruct()` is not retryable through preflight. | Governed recovery. |
| 9. Fresh context capture | `current_basis()` reads with a separate repeatable-read transaction and SHARE lock; `capture()` owns another repeatable-read transaction that inserts context and audit together after basis and inventory checks. | Reads fenced basis; writes a fresh recovery context and audit, not new operator or execution authorization. | Capture failure rolls back context/audit and leaves committed bootstrap fence. Full reconstruct retry is denied on a populated target; an internal recovery-entry retry can capture a new context. | Governed recovery. |

## Candidate invariants

| Invariant | Status | Evidence and limit |
| --- | --- | --- |
| C3-I1 Archive authority isolation | Supported for canonical `security_state` | The restore-list comments out its table-data entry and migration-ledger data. Historical authorization and recovery rows do import, but are not current merely by being present; current authority is established by separate metadata/bootstrap logic. |
| C3-I2 Historical authority reconstruction | Supported | `_apply_restored_authority()` sources state, version and epoch from the parsed manifest after digest/preflight checks. The manifest and dump are correlated by an unkeyed hash, so “validated” does not mean authenticated against an external publisher. |
| C3-I3 No authority manufacture by mechanics | False as phrased | Mechanics issues no new context, operator grant or execution grant, but commits canonical state/version/epoch from the manifest with `recovery_bootstrap_pending=false`. For `NORMAL`, normal capability checks allow ordinary effects in this interval. |
| C3-I4 Explicit recovery transition | Supported for the public workflow; partially supported as a general boundary | `reconstruct()` calls mechanics then `_enter_recovery()`. The internal `_restore_verified_data()` is already callable by tests and leaves an unfenced target. |
| C3-I5 Fail-closed recovery entry | Supported once bootstrap commits | Existing capture-failure test shows effective `RECOVERY_REQUIRED` persists. It does not cover failures before the bootstrap commit; those are the unsafe interval. |
| C3-I6 Public workflow preservation | Supported | CLI accepts backup path and `--pg-restore`, calls only `reconstruct()`, and reports success after a fresh context ID. No restore-only flag exists. |
| C3-I7 Honest verification claim | Supported if documented narrowly | Production compares authority metadata and migration inspection, then checks three tables are queryable. The M2 integration helper separately compares selected ordered row projections plus snapshot/report outputs for a canonical fixture; even that is projection-based, not universal semantic equivalence. |

## Existing and added characterization

Existing unit coverage pins restore flags/credentials and protected TOC exclusion plus FK ordering. Preflight integration pins valid/pristine, digest, malformed manifest, version/schema/checksum mismatch and populated-target rejection. Reconstruction integration pins full recovery entry across stored states, version/origin and fresh context, failed `pg_restore`, malformed authority, capture-failure fencing, and a real `pg_dump`/`pg_restore` round trip with M2 projection equivalence in two fixture variants. Authority bootstrap and recovery-context suites cover fence behavior, capability denial, context replay, audit atomicity and concurrent basis handling. Backup inspection/creation and credential-sentinel suites supply adjacent evidence.

Added tests pin: direct mechanics return state for each `SecurityState` (including a source pending flag), no new context/authorization rows, and the `NORMAL` capability exposure; failures at authority application, migration, inspection and critical-table check after a committed import, with non-pristine retry denial; `reconstruct()` ordering; and CLI rejection of restore-only/skip-recovery flags. Tests simulate post-import failures with a committed runner, so they characterize the application phase boundaries rather than proving the external tool's transaction behavior. No tests were added for contracts already pinned by existing suites.

## Architectural answers and Pass 2 recommendation

`_restore_verified_data()` is the existing mechanical boundary by call graph, and recovery bootstrap/context capture rightly remain on the governed side. It is **not a safe standalone service boundary** today because it commits an unfenced historical authority row. Its `DatabaseReconstructionResult` and “verified data” name can overstate validation: production does not run the test-only source/restored equivalence drill, and the same result type represents both pre-recovery and completed recovery depending on whether `recovery_context_id` is `None`.

Extracting mechanics into an independently callable component would make an existing private test seam easier to reuse unsafely. The full public workflow must retain mechanical import immediately followed by governed recovery entry, with no public restore-only mode. Before a safe extraction, Pass 2 needs an explicit answer for failures after successful import but before bootstrap and for the unfenced success interval. This is a C3 design constraint, not a request to redesign reconstruction in Pass 1. A `NORMAL` manifest reproduces ordinary effective authority in that interval. The target is populated, preflight rejects a second full run, and there is no automatic rollback across the child import, authority update, migrations and bootstrap.

Restore-list planning has a meaningful contract (protected table-data exclusion, duplicate detection and FK order), but no independent lifecycle, transaction or caller. Keep it inside mechanics in C3; file size alone is insufficient reason to extract it.

The smallest viable Pass 2 boundary is an internal mechanics unit covering preflight, restore-list planning, `pg_restore`, manifest-derived authority application, migrations and limited post-restore checks, invoked solely by a public orchestrator that then performs recovery bootstrap and context capture. Make its pre-recovery result explicitly named for its limited checks and keep it inaccessible as an operator workflow. Do not perform that extraction until the unfenced interval and post-import failure policy have been resolved without weakening the supported restore-to-recovery path. If C3 cannot preserve the existing M2 authority reconstruction and simultaneously make that interval safe, redesign the proposed boundary or abandon the extraction rather than presenting the split as an invariant-preserving refactor.
