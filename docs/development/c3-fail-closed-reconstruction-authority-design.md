# C3 Pass 1B — Fail-closed reconstruction authority design analysis

Date: 28 September 2026. Design analysis only; no production implementation or mechanics extraction. This follows [Pass 1](c3-reconstruction-mechanics-pass1.md).

## Decision

The fence must commit **before `pg_restore` can commit imported rows**. Fencing only during or after manifest authority reconstruction leaves a populated target running under its pristine `NORMAL` singleton for some interval or after an interruption. The smallest design supported by current domain vocabulary is to use the existing durable recovery-bootstrap fence before import, then atomically finalize the historical origin, version and epoch **without clearing that fence**. This is a C3a authority/failure-contract change, not a mechanical extraction. C3b can extract mechanics only after C3a is verified.

This recommendation needs implementation design review and characterization before coding. In particular, using the existing bootstrap on the pristine target first creates a provisional origin (`NORMAL`, version 1, target epoch). The finalization transaction must replace that provisional origin with validated manifest provenance before any context capture. That changes how bootstrap metadata is established during reconstruction, although the final post-reconstruction basis can remain equivalent to M2. It must be an explicit reconstruction-specific boundary, not an accidental invocation of `initialize(RECOVERY)` that is assumed to have captured the source origin already.

## Consumer map

| Restored value | Consumers and required meaning |
| --- | --- |
| Historical `security_state` S | `BackupStateInspectionService` records effective source state in the manifest; `DatabaseReconstructionService` currently compares that state after import. `AuthorityBootstrapService` currently copies raw S into `recovery_bootstrap_from_state`; `read_recovery_authority_basis` exposes it as origin, and `RecoveryContextService._incident` uses it for incident identity. `SecurityStateStore` exposes `RECOVERY_REQUIRED`, rather than raw S, when pending. Capability and transition services depend on that pending fence. The M2 equivalence drill compares the raw singleton and transition history. S does **not** need to be unfenced current authority; it can remain raw historical provenance under a pending fence. |
| Historical version V | Manifest creation and production validation read it; bootstrap origin and context identity/basis use it, with `RecoveryAuthorityBasis` requiring current version greater than origin V. Recovery-context, authorization and audit rows bind current version; restoration advances it, and epoch replacement advances it again. Historical imported records retain their original version. The compatible fenced current value is V+1, origin V. V does **not** need to be exposed as the unfenced current version. |
| Historical epoch E | Manifest creation/validation and the current reconstruction write use it. Recovery basis/context, new recovery authorization, restoration audit, and `complete_reconstruction()` expect E until atomic restoration and replacement rotate to a fresh epoch. Historical imported authorization/audit rows remain attributed to E. `AuthorityEpochId` grants no capability by possession, but epoch-only freshness checks make the pending fence and context binding important. Keeping E as the fenced current epoch preserves M2 lineage and the existing recovery path. A new target epoch would require broader changes to recovery authorization and historical attribution. |

The manifest records a source **effective** state and pending boolean, not the source bootstrap timestamp or origin fields. If the source was already pending, its manifest state is `RECOVERY_REQUIRED`; reconstruction deliberately creates a fresh target bootstrap incident. Archive `security_state` data remains excluded. Imported historical authorization/context rows do not replace the freshly captured context, and `complete_reconstruction()` rotates E before restored ordinary authority is visible. `AuthorizationService.require_current_execution()` checks epoch/time rather than version, so a restored E alone is not a sufficient safety fence; downstream effect and recovery-context checks must remain intact.

## Why current code clears then bootstraps

`_apply_restored_authority()` clears pending and all origin fields while writing S/V/E, and `_enter_recovery()` subsequently invokes `AuthorityBootstrapService.initialize(RECOVERY)`. That gives the existing bootstrap exactly the raw source-derived row it expects: it copies S/V into origin, increments to V+1, sets a new timestamp and pending flag. It also discards any source pending flag and unavailable source origin metadata, satisfying migration 024's all-or-nothing bootstrap shape constraint. The need for a **fresh** target origin is real; an intermediate committed **unfenced** row is not established as an invariant. It is a consequence of composing two separately committed operations.

## Candidate comparison

| --- | --- | --- | --- |
| A. On its own it has the wrong origin, version and epoch for restored history. Existing bootstrap is idempotent while pending and will not replace origin after import. **Immediately after import:** too late; the target's pristine `NORMAL` singleton remains current while imported rows persist. | Before import failure leaves a fenced target to discard; after-import placement leaves the established unsafe gap. Needs a separate atomic provenance finalization and revised production verification. No schema needed if combined with D. | Necessary early-fence primitive, insufficient alone. |

## Failure matrix

“P” is the pristine target epoch; “E” is the manifest historical epoch. The table gives D's durable state after a phase fails. The full operator command reports failure in every row; it never treats a fenced partial import as a successful restoration.

| Failure point | Durable authority and data under D | Retry |
| --- | --- | --- |
| Before preflight/restore-list planning completes | Initial pristine `NORMAL`/v1/P; no imported data. | Correct input and retry if target remains pristine. |
| After preflight/planning, before early-fence commit | Same pristine state; no imported data. | Retry normally. |
| After early-fence commit, before `pg_restore` | Raw `NORMAL`/v2/P, pending=true, provisional origin `NORMAL`/v1; effective `RECOVERY_REQUIRED`; no imported data. | Discard/recreate. Pristine data check might pass, but a fresh-mode/authority check is not a license to reuse a partial attempt. |
| During or after `pg_restore`, before provenance finalization | Same provisional fence; child transaction rolls back on failure or leaves imported rows on success. Effective authority remains `RECOVERY_REQUIRED`. | Discard/recreate; do not weaken pristine preflight or resume partial import. |
| During authority finalization transaction | Either provisional fenced state (rollback) or finalized fenced state (commit); never an unfenced committed S/V/E row. Data may be imported. | Discard/recreate. |
| During migrations | Finalized raw S, current V+1, E, pending=true, origin S/V; schema/ledger may be partially advanced across migration transactions. | Discard/recreate. |
| During validation | Same finalized fenced authority; imported data and completed migrations remain. | Discard/recreate. |
| During context capture | Same finalized fence; context/audit capture transaction rolls back together. No fresh context ID is reported. | Discard/recreate is sufficient for the public workflow. An internal context-capture retry is technically possible but is not required for C3 and must not become a public restore-only/resume mode. |

The early-fence version is tied to P and is provisional. Finalization changes epoch to E and sets version V+1, which is greater than origin V; version numbers are meaningful within an epoch, so this is a lineage switch, not a decrement in the restored epoch. The final raw state may be `NORMAL`, `DEGRADED`, `LOCKDOWN`, `COMPROMISED_SUSPECTED` or `RECOVERY_REQUIRED`, but `SecurityStateStore` always exposes effective `RECOVERY_REQUIRED` while pending. If the source manifest says pending, the target still establishes a new incident with origin `RECOVERY_REQUIRED`/V; it does not reuse source bootstrap metadata.

## Equivalence, schema, and retry

The existing M2 test compares the source and target **before** bootstrap, including the raw `security_state` row (apart from `updated_at`). D deliberately removes that unfenced comparison point. Keep the comparison's research, evidence, history, authorization, migration, snapshot and report projections, but compare source S/V/E against the finalized target's raw S, origin S/V and E with an explicit expected fence/version delta. Do not simply omit the security group. Production checks should assert this finalized shape and critical-table accessibility; they still must not claim full M2 equivalence.

D requires no new persisted state, domain enum, manifest field or migration **on the inspected schema**: migration 024 accepts a pending row with raw S, valid origin S/V and timestamp, and `RecoveryAuthorityBasis` accepts current V+1. It does require a reconstruction-specific authority finalization operation and a changed phase order. The existing recovery/reconciliation code can consume the final basis unchanged; the provisional basis must never be used to capture a context. No existing requirement establishes resumable reconstruction. Continuous fencing makes discard/recreate a sufficient failure model for this bounded operator workflow; preserving pristine-target preflight is part of it.

## Characterization needed before C3a implementation

1. Prove on a disposable target that the pre-import `RECOVERY` bootstrap commits a fence before any child import, and a failed `pg_restore` leaves it pending. Capture the exact provisional state and show `CONTINUING` remains restricted.
2. Pin atomic finalization across source `NORMAL`, restrictive states and source-pending manifests: raw S, origin S/V, current V+1, E, timestamp, effective `RECOVERY_REQUIRED`; no intermediate unfenced commit and no new grants/contexts.
3. Inject failure after import and at authority finalization, each migration and validation, and context capture. Assert the durable fence at every point and require discard/recreate rather than full retry on the same target.
4. Check historical authorizations and contexts cannot be used for current effects while fenced; a fresh context binds the finalized basis, and baseline/restrictive reconciliation plus atomic restoration/epoch rotation retain their behavior.
5. Adapt the real `pg_dump`/`pg_restore` M2 drill to compare historical source projections with the finalized fenced target, including explicit S/V/E provenance assertions, while retaining its other projection checks.
6. Pin that the public CLI still runs one complete workflow and reports a context only after capture. Keep protected table-data exclusion, restore-list planning and `pg_restore` flags unchanged.

Pass 1 already characterizes the **current unsafe** state. Those tests are expected to change in C3a rather than be mistaken for desired behavior. No further tests or production files were changed in Pass 1B.
