# C3a Pass 2B — Reconstruction readiness gate design

Date: 28 September 2026. Design analysis only. No production code, schema, manifest, tests, or C3b mechanics extraction changed.

## Finding and recommendation

No existing durable primitive truthfully means “the reconstructed target passed production validation and may now capture a fresh RecoveryContext.” Recommend Design A: atomically install the **final manifest-derived E/S/V recovery fence and a minimal persisted validation-pending gate before `pg_restore`**, then clear that gate only after successful production reconstruction checks. The gate belongs beside the singleton `security_state`, whose lock already serializes context-basis reads and authority changes. This recommendation is conditional on preserving the supported trust boundary: normal application writes obey the pending fence, and competing privileged restore/migration jobs must be serialized or excluded from this target. A boolean gate alone cannot make arbitrary direct SQL tampering or uncoordinated schema jobs safe.

A possible schema name is `reconstruction_validation_pending BOOLEAN NOT NULL DEFAULT FALSE`. `FALSE` preserves legacy ordinary recovery. The pre-import transaction sets it `TRUE` together with raw S, origin S/V, current V+1, E, pending=true and a fresh bootstrap timestamp. The production-validation publication transaction changes only readiness to `FALSE` after rechecking the fenced authority/provenance and the required production validations. This is a design proposal, not an implemented SQL contract. The source manifest/backup format needs no field. The ORM mapping and narrow trusted readers/writers need updates; `RecoveryAuthorityBasis` and RecoveryContext JSON need not change if the gate is checked separately under the same singleton lock.

## Search for an existing readiness primitive

| Candidate value | Why it is not authoritative reconstruction readiness |
| --- | --- |
| `recovery_bootstrap_pending`, origin S/V, `started_at` | All are valid before import. They establish restrictive authority and incident origin, not successful restore, migration, or validation. A source backup can itself be pending. |
| `RecoveryContext` row, incident ID, inventory status | Historical rows import from the archive; a new context can currently be captured before import. A context is the product to gate, not proof of readiness. Its inventory is a bounded evidence snapshot, not reconstruction validation. |
| Manifest metadata, dump digest, backup directory | They validate input/correlation, not target completion. They are not a durable target-side readiness decision. |
| Migration ledger or schema version | The pristine target is already migrated before import; the same ledger exists before and after successful restore. A migration can commit independently of later validation. |
| `security_state_transitions`, authorization/audit records, Authority Epoch E or version V+1 | Historical rows can be imported; bootstrap does not append a transition; E and V+1 can be installed before import. Authorization records can be created while fenced and do not prove the target was validated. |
| Provider/cycle attempt statuses, task fingerprints, evidence fingerprints | These are task/attempt-local state and can be imported from the source. They do not attest to database reconstruction. |
| `DatabaseReconstructionResult`, CLI success, temporary restore list | Process-local or temporary; lost on crash and invisible to concurrent services. |

No existing status or phase enum in the inspected persistence/domain contracts carries the required target-wide assertion. Reusing one would give it a second incompatible meaning.

## Design comparison

| --- | --- | --- |

After validation, publisher clears gate in one transaction under singleton `FOR UPDATE`; capture reads gate under `FOR SHARE` in its own transaction and either fails or sees committed readiness. Recheck validation-relevant state in the publication transaction; serialize privileged migration/restore jobs separately. | No P→E epoch switch. Final basis is M2-compatible (S/V origin, current V+1, E); source-pending backup starts a fresh incident. One boolean column, ORM field and narrow gates. | B. Bootstrap phase | Add an explicit `reconstruction_in_progress` versus `recovery_ready` phase to the bootstrap singleton. ## Exact authority states and phase failures under A

Let validated manifest values be state S, version V ≥ 1, non-nil epoch E. Pristine target starts raw/effective `NORMAL`, version 1, epoch P, pending=false, gate=false, with no restored data. After input/preflight/list planning, a single committed pre-import transaction sets raw S, origin S/V, current version V+1, E, pending=true, new started-at, gate=true. Effective state is `RECOVERY_REQUIRED`. The target already has **final** historical E, so no provisional P-bearing context or authorization can arise after this transaction. Archive `security_state` table data is excluded; other imported rows do not require the canonical row to be absent or pristine. Preflight is completed before this write. A failure during/after `pg_restore`, finalization, migration or validation leaves gate=true and pending=true; discard/recreate remains the public retry model. There is no post-import P→E finalization step in this design.

After successful data import, migration and production checks, readiness publication commits gate=false while preserving raw S, origin S/V, current V+1, E, pending=true and effective `RECOVERY_REQUIRED`. A fresh RecoveryContext may then be captured against that unchanged M2 basis. If capture fails, the target is **recovery-ready but still fenced**; no context is reported. Later governed recovery and `complete_reconstruction()` retain the M2 path: reconciliation, fresh authorizations, atomic protected restoration plus epoch replacement, then ordinary `NORMAL` authority under a new epoch. The gate does not grant authority and need not advance the security version, provided all current-context/use paths also check it when required. The completed recovery transition clears the existing pending fence as today. A gate left false after completion is harmless; a later new reconstruction on that populated target remains prohibited by preflight.

If a source backup was already pending, `BackupStateInspectionService` records its **effective** `RECOVERY_REQUIRED`/V/E and `recovery_bootstrap_pending=true` but omits its origin/timestamp. Pre-import installation uses S=`RECOVERY_REQUIRED` as a new raw origin with fresh target timestamp, current V+1, E and gate=true. It does not resume or reuse the source incident.

## Gate location and authorization paths

The deterministic capture check belongs in `RecoveryContextService.capture()` **inside its existing repeatable-read transaction**, after locking the singleton row in SHARE mode and **before** the idempotent-existing-context branch. `current_basis()` may remain available for diagnostics, but must not itself imply capture eligibility. `read(require_current=True)` and protected restoration should reject a blocked gate if a context somehow exists while validation is pending; this is a narrow defense for imported or previously created records without changing the basis model. Reconciliation is read-only; it may report unavailable/fail closed rather than authorize an effect while blocked.

Gating capture **alone is insufficient** for the strict temporal authorization contract. `AuthorizationService.issue_operator()` and `issue_execution()` do not verify that a referenced RecoveryContext exists; `recovery_context_id` and issuance-basis IDs are supplied by the caller. A recovery-bound authorization can therefore be issued for a caller-chosen future context ID before publication, then potentially match a newly captured context with that ID. Gate **new recovery-bound issuance while validation is pending** under the same singleton SHARE lock. This blocks a caller-chosen future context ID from being pre-authorized before readiness. After publication, retain the existing M2 issuance contract; requiring the context row to exist at issuance would be a separate, broader change. Exact historical replay may remain historical-only; it must not become an effect permission. Do not broaden `require_current_execution()` into a universal effect gate: its existing epoch/time/context-ID result is subordinate to protected restoration's current-context and reconciliation checks. Authorization lacking a context can still be recorded under current APIs, but cannot satisfy protected reconstruction restoration's context binding; review any other effect consumer before implementation.

The narrowest authoritative check can be a shared read of the singleton gate used specifically by capture, recovery-bound issuance, `read(require_current=True)`, and protected restoration. This avoids requiring every safe diagnostic reader to treat readiness as authority and avoids silently changing RecoveryContext's serialized basis. It remains an additional rule future recovery-entry code must honor; tests and documentation should make that explicit.

## Validation publication and races

The existing **production** success criteria, not the M2 source/restored equivalence drill, are: validated manifest and dump hash; pristine compatible target and migration checksums; selected restore list with protected table-data exclusion and dependency order; successful single-transaction `pg_restore`; final fenced S/V/E/origin row; successful local migrations; post-restore inspection of database/migration/authority metadata; and accessibility of the migration, security and task tables. For A, change the authority comparison from unfenced S/V/E to the final fenced S/V/E, pending=true, origin S/V, V+1, gate=true. Do not claim row-by-row, snapshot or report equivalence in production.

The publication transaction should lock the canonical singleton `FOR UPDATE`, require gate=true, pending=true, exact expected E/S/V/V+1/origin, and confirm the relevant final inspection/critical-table checks in a consistent snapshot before setting gate=false. Hold the migration advisory lock if migration/ledger state is part of the validation, or otherwise prevent concurrent migration jobs. Capture's singleton SHARE lock spans its gate check, basis/inventory read, context/audit insert and commit; a capture racing publication either sees blocked readiness and fails, waits for the committed publication and reads ready, or receives a serialization conflict and fails closed. No process-local success bit may be substituted.

The singleton lock only serializes actors that also lock it. Existing ordinary application mutation is denied while pending, but a privileged direct writer or another restore/migration job could alter data without that lock. C3a must specify exclusive target ownership or a database-level role/job lock obeyed by those privileged writers for the validation-through-capture interval. Without it, no one-bit readiness design can prove absence of unnoticed post-validation changes. `BackupCreationService`/state inspection should also reject gate=true if partial targets must not become published backup sources; otherwise backup can export incomplete reconstructed data. These are bounded trust assumptions and required implementation checks, not a claim of universal tamper resistance.

## Tests required before implementation

1. Assert the pre-import transaction commits S/V/E, origin, pending fence and gate=true atomically before the child data import; inject rollback and process failures and verify no unfenced committed state.
2. Cover all manifest states, V=1 and higher, E different from pristine P, and source-pending manifests. Check no provisional P epoch-bearing rows are created after the pre-import commit.
3. Capture, current-context read, new recovery-bound operator/execution issuance, reconciliation and protected restoration must deny while gate=true, including caller-chosen future context IDs and imported historical records. Preserve post-readiness issuance semantics. Keep safe diagnostics available if intended.
4. Publish readiness only after each production check; inject import, migration, inspection, critical-table and publication failures. Assert durable gate=true and pending=true; verify discard/recreate remains the documented retry.
5. Race capture against publication using separate database connections and barriers. Assert no pre-commit capture, no stale-snapshot acceptance and correct post-commit basis. Race competing migration/restore jobs according to the chosen exclusive-target mechanism.
6. Capture after publication must bind S/V/E and V+1; capture failure leaves gate=false but pending=true. Existing baseline/restrictive reconciliation and atomic restoration/epoch rotation still work.
7. Adapt the real M2 drill only where raw unfenced authority equality is no longer semantically valid; retain all other source/restored projections and security transition history. Assert the production check makes no equivalence claim.
8. Verify a blocked target cannot be used as a backup source if that guard is adopted; verify legacy ordinary recovery and upgrade semantics with the field default.

## Proposed C3a production slice

C3a should add the singleton validation-pending field, an atomic pre-import manifest-derived fenced write, a validation-and-publication transaction, and narrow recovery-entry/authorization gates, while preserving the public one-command workflow and strict preflight. It should include the targeted race, failure, source-state and M2 drill tests above. This is the smallest design found that supplies a durable readiness decision without a new security state or a second authority table. C3b mechanics extraction remains deferred.
